# Amazon SES Frankfurt

Last verified: **2026-08-23**. Official references: SES
[regions](https://docs.aws.amazon.com/ses/latest/dg/regions.html),
[verified identities and Easy DKIM](https://docs.aws.amazon.com/ses/latest/dg/send-email-authentication-dkim-easy.html),
[custom MAIL FROM](https://docs.aws.amazon.com/ses/latest/dg/mail-from.html),
[DMARC](https://docs.aws.amazon.com/ses/latest/dg/send-email-authentication-dmarc.html),
[SMTP credentials](https://docs.aws.amazon.com/ses/latest/dg/smtp-credentials.html),
[SMTP TLS](https://docs.aws.amazon.com/ses/latest/dg/smtp-connect.html),
[sandbox exit](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html), and
[suppression](https://docs.aws.amazon.com/ses/latest/dg/sending-email-suppression-list.html).

Select `eu-central-1` before every SES action. Identity, quota/sandbox status,
suppression, SMTP credentials, and configuration sets are regional.

### `SES-01` — Create the dedicated sending identity

- **Owner:** AWS account owner.
- **Action:** In AWS select **Europe (Frankfurt) `eu-central-1`**, open **SES → Configuration → Verified identities → Create identity**, choose a dedicated sending subdomain, and enable Easy DKIM. Use a separate dedicated MAIL FROM subdomain.
- **Expected result:** SES shows the identity and three generated Easy-DKIM CNAME records in Frankfurt.
- **How to verify:** confirm the console region and identity details before touching DNS.
- **Evidence:** `region=eu-central-1`, identity class `domain`, DKIM mode, status, and date—no domain/record value.
- **Rollback:** delete the empty wrong-region identity and recreate it in Frankfurt.
- **NEVER PASTE HERE:** domain/email, generated DNS values, AWS account ID, console URL, credentials, or identity export.

### `SES-02` — Publish authoritative DNS records

- **Owner:** authoritative-DNS account owner.
- **Action:** At the authoritative DNS provider—not Pangolin—add SES identity verification/Easy-DKIM CNAME records, custom MAIL FROM MX and SPF TXT, and DMARC TXT aligned through DKIM and/or SPF. Use exactly the values generated by SES in Frankfurt.
- **Expected result:** SES reports identity/DKIM verified and MAIL FROM success; external DNS shows correct record types without a private App target.
- **How to verify:** use SES **Authentication** state and read-only DNS queries for CNAME/MX/TXT types. Review DKIM/SPF/DMARC on one sandbox-safe message later.
- **Evidence:** record type/purpose/status, SES region, verification date, and redacted authentication result.
- **Rollback:** disable sending first, then remove only the SES records; verify SES returns pending/failed as expected.
- **NEVER PASTE HERE:** owner domain, record names/values, verification token, account ID, DNS credential, or message headers containing identity.

### `SES-03` — Create the staging configuration set

- **Owner:** AWS account owner in Frankfurt.
- **Action:** Open **SES → Configuration → Configuration sets → Create set**, name the protected staging set, enable required reputation/delivery options, and configure account-level suppression. Keep bounce/complaint evidence owner-only until Stage 09 adds automated event handling.
- **Expected result:** a Frankfurt configuration set and suppression policy are active.
- **How to verify:** read the configuration-set/suppression status and use the mailbox simulator in a later bounded test.
- **Evidence:** configuration-set class/reference, suppression options, region, result, and date.
- **Rollback:** stop sending, remove event destinations/settings, then delete the empty set if no delivery dependency remains.
- **NEVER PASTE HERE:** configuration-set/account IDs, event destinations, recipient/message IDs, bounce detail, email, or credentials.

### `SES-04` — Create the Auth0 SMTP identity

- **Owner:** AWS IAM/SES owner.
- **Action:** Create SES SMTP credentials dedicated to Auth0 Frankfurt sending. Store them directly in Auth0's email-provider store; do not reuse them as AWS API credentials or App variables.
- **Expected result:** the identity can authenticate to the Frankfurt SMTP endpoint with required TLS and send only from the verified identity.
- **How to verify:** one Auth0 OTP to the verified owner/sandbox-safe recipient succeeds; a non-SES AWS API action with the SMTP credential is unavailable.
- **Evidence:** credential class, region/TLS, allowed send result, denied unrelated action, rotation date.
- **Rollback:** disable Auth0 sends, replace/verify, delete the old SMTP credential, and verify it fails.
- **NEVER PASTE HERE:** SMTP username/password, recipient/sender, OTP/body/header/message ID, endpoint/account ID, or Auth0 config export.

### `SES-05` — Create the separate App sender identity

- **Owner:** AWS IAM/SES owner.
- **Action:** Create a separate staging IAM principal/access key for later App email, limited to required SES send and configuration-set/receipt operations in Frankfurt. Give it no R2, Polly, IAM, or account administration access. Keep product email disabled until Stage 09.
- **Expected result:** safe simulator send is allowed; unrelated AWS actions and an unverified From identity are denied.
- **How to verify:** policy simulator/negative calls plus one SES mailbox-simulator call at the later checkpoint.
- **Evidence:** principal class, allowed/denied action classes, region, result, and date.
- **Rollback:** disable the App email adapter, rotate/delete key, and verify old access fails.
- **NEVER PASTE HERE:** IAM ARN/user name, access key/secret, policy export with private IDs, From/recipient, message/body, or response.

### `SES-06` — Verify sandbox-safe delivery

- **Owner:** account owner after identity and credentials are ready.
- **Action:** While SES is in sandbox, send at most one minimal non-product OTP/template to the verified owner identity or SES mailbox simulator using the staging configuration set. Send no learner content, goal, date, response, Readiness, or raw data.
- **Expected result:** SES accepts the request; delivery/simulator outcome and DKIM/SPF/DMARC are observable; bounce/complaint policy is visible.
- **How to verify:** read the SES console and receiving-header authentication result without retaining body, address, or linkable message ID.
- **Evidence:** region, configuration-set class, outcome/authentication categories, bounded count=1, cleanup, and date.
- **Rollback:** disable the sender/credential and correct DNS/provider configuration; never add a password fallback for OTP failure.
- **NEVER PASTE HERE:** address, body, subject, message ID, headers, credential, domain/DNS value, provider response, or screenshot with any of them.

### `SES-07` — Set quotas, alerts, and feedback ownership

- **Owner:** AWS billing/operations owner.
- **Action:** Set owner-chosen AWS budget alerts and review SES regional sending quota, sandbox status, reputation, suppression, and feedback ownership. Keep a protected contact/escalation record.
- **Expected result:** alerts and an owner exist; staging remains within a bounded envelope.
- **How to verify:** read dashboard state and alert test/status without disclosing amount/contact if private.
- **Evidence:** `budget_alert=verified`, quota/sandbox categories, owner role, date, and result.
- **Rollback:** set product email/OTP closed, reduce/revoke sending access, and retain in-App/fake behavior.
- **NEVER PASTE HERE:** billing/contact detail, quota request correspondence, sender/recipient, account ID, or credential.

### `SES-08` — Gate production access and exit

- **Owner:** AWS account owner; production-visible authority.
- **Action:** Request production access only after domain authentication, bounce/complaint handling, sending description, owner approval, privacy review, and later Stage 09 behavior exist. For provider exit, export only configuration/aggregate suppression obligations allowed by policy, validate alternate SMTP, switch App/Auth0 separately, then revoke SES identities.
- **Expected result:** sandbox is sufficient for owner-only staging; production access remains a named launch gate, never a Stage 02 completion claim.
- **How to verify:** inspect sandbox/production status and later substitute-provider delivery/authentication without exposing recipients.
- **Evidence:** gate state `owner_pending`/`verified`/`failed`, configuration digest, transition/rollback result, and date.
- **Rollback:** remain in sandbox with product email disabled after denial; restore the verified predecessor only while valid.
- **NEVER PASTE HERE:** production-access form, legal/billing/contact detail, domain/address, suppression export, messages, or credentials.
