## 1. Project context you must preserve

Bestehen / App is a personal German exam coach for a learner who may begin around A1 and wants to pass **TELC Deutsch B1**. It teaches through exam preparation: Observe → Attempt → Diagnose → Repair → Retry → Remember. It covers Reading, Language Elements, Listening, Writing, and Speaking; maintains learner evidence and Mistake Memory; recommends one highest-value daily action while allowing deliberate choice; progresses each task family independently toward target conditions; and provides evidence-based Readiness, mocks, and Ready-to-Book guidance.

Bestehen / Corpus is a separate exam-data/intelligence product. Corpus owns provenance, authenticity/confidence, rights metadata, deduplication, taxonomy, difficulty/relevance, and publication eligibility. App owns learner state, approved practice, coaching, evaluation, evidence interpretation, Readiness, and UX. Routine learner work uses App-approved, cached/versioned content and intelligence; it does not search raw Corpus or invoke Corpus AI per click.

TELC B1 has independent Written and Oral pass gates. An overall total cannot compensate for failure in either. The official pass line (60%) and Bestehen's versioned Safe default (65 plus breadth/range/confidence/currentness rules) are distinct. The launch Readiness index is a target-performance estimate bottlenecked by the weaker component, not a chance of passing. No pass-probability field, model, event, copy template, or hidden calculation is allowed before independent empirical calibration and the product gate permit it.

The finalized design comprises one semantic token system in light/dark modes, Bricolage Grotesque + IBM Plex Sans + IBM Plex Mono, a shared five-skill component library, 24 mobile screens, responsive tablet/desktop rules, Flows A–G, explicit accessibility/recovery states, and the Concept B / B1 Threshold B logo. The design is a behavior/layout contract where consistent with product truth; its runtime code is not a framework mandate.

Launch is responsive web, phone-first for daily coaching with stronger large-screen Writing/Readiness/mock layouts. Core first use is account optional. WCAG 2.2 AA, local capability degradation, draft/checkpoint/timer integrity, export/deletion, privacy, rights, bounded AI, and low-ops personal-project sustainability are architecture requirements—not later polish.

## 7. Product and design invariants relevant to this stage

- Validity and fairness outrank direct evidence, which outranks independent Written/Oral pass risk, uncertainty resolution, due repair/retention, progression/coverage, and preference.
- Learning evidence and Readiness evidence differ; direct modality, assistance, timing, exposure, freshness, independence, validity, affected scope, and evaluator confidence remain explicit.
- A technical, content, media, accessibility, browser, network, or evaluator failure never becomes learner failure. Pending blocks only dependent conclusions.
- Written and Oral are independent pass gates. Missing estimate is absence, not zero. Safe is not Ready to Book. No pass probability is permitted before the empirical gate.
- Five skills share one session/attempt/result/repair/evidence foundation; P0–P4 are local condition profiles, not a global level.
- Corpus supplies asynchronous rights-aware intelligence and approved bundles; ordinary learner attempts do not call live Corpus search/AI and Corpus receives no learner profile.
- Responsive web, WCAG 2.2 AA, account-optional first use, export/delete, bounded AI, ephemeral raw audio, deterministic/cached defaults, and personal-project sustainability are mandatory architecture constraints.
- Release units carry versions and targeted revalidation; blueprint/evaluator changes never silently reinterpret history.
- Avoid enterprise process/infrastructure without a personal-project requirement.

### Must not reopen

- complete product can be phased.
- no misleading readiness during partial rollout.
- separate content/model/blueprint versioning.

If a mutable empirical number appears, preserve the shaped behavior while treating the number as a versioned calibration parameter with provenance, effective date, validation evidence, and rollback. Do not create meaningless abstraction around stable product rules.

## 8. Research and decision-making rules

- Trace every architecture decision to exact product/design source paths and, where practical, sections/anchors. Give each consequential decision a stable `ARCH-S26-DNN` identifier and link an ADR when one exists.
- Prefer the smallest maintainable architecture that preserves the complete exam-coaching goal. Complexity must answer a measured requirement, failure domain, security boundary, or operating need.
- Use current official primary documentation for frameworks, services, APIs, browser capabilities, codecs, security guidance, pricing, quotas, limits, region behavior, SDKs, and support lifetimes. Record direct links and access date. Do not select mutable commercial services from memory.
- For every commercial/provider choice, state recurring/variable/egress/storage/maintenance/exit costs, a cheaper fallback, export/migration path, and measured upgrade/substitution trigger. Do not invent a fixed euro budget the owner did not provide.
- Favor deterministic scoring/Readiness/review/planning, cached pre-generated routine content, batched media, asynchronous Corpus publication, bounded productive evaluation, and one source of truth.
- Reject by default per-click premium AI, routine runtime objective-question generation, always-on AI summaries/analytics, expensive real-time voice where turn-based suffices, microservice-per-domain, Kubernetes, event-streaming platforms, multi-region, speculative million-user capacity, and an analytics warehouse before evidence demands them.
- Ask an owner question only when unavailable preference, legal-risk tolerance, or budget materially changes the architecture. Ask one precise question, explain impact, and include a recommended default. Otherwise decide and document.
