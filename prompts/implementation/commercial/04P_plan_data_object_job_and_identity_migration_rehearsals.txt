Read and obey `prompts/implementation/COMMON_STAGE_CONTRACT.md`. Planning is read-only. Do not freeze production, copy sensitive data, change DNS, or mutate Coolify/Render/provider state.

Objective

Plan repeatable production-shaped rehearsals from the Coolify-hosted PostgreSQL/application profile to Render Frankfurt without losing, duplicating, reassigning, resurrecting, or silently reinterpreting canonical data. Keep R2 and Auth0 stable unless isolation or test evidence requires a compatible copy/reconfiguration.

Planning responsibilities

1. Define the source and destination inventory/preflight: PostgreSQL exact versions/extensions/collations/timezones, schemas/migrations, sizes/growth, large tables, constraints/sequences, jobs/leases, R2 manifests, Auth0 links, app-owned IDs, release pins, backups, tombstones, deletion/provider-pending journals, and local-client compatibility.
2. Select and justify the smallest safe migration method using official Render/PostgreSQL capabilities: dump/restore, logical replication, or another compatible path. Define downtime envelope, prerequisites, test data sanitization, encryption, transfer custody, and failure modes.
3. Define application/web/worker compatibility and quiescence: exact old/new versions, write freeze or dual-compatible window, migration lease, queue pause/drain, in-flight jobs, scheduled work, late provider callbacks, R2 uploads, exports/deletions, and foreground WAL.
4. Define ordered backup, schema, roles, data, sequence, index/constraint, job, projection/cache, object-reference, identity/callback, and release-manifest steps. Derived state may be rebuilt only from canonical facts with version pins.
5. Define validation at multiple layers: row/constraint/sequence counts, sampled and full hashes where safe, canonical ledger replay, projection equivalence, ownership/isolation, job states/idempotency, object existence/digests, identity links, tombstones/deletion suppression, audit continuity, and application smoke tests.

7. Define Auth0 disposition and callback/origin change while preserving app-owned IDs, sessions/recent-auth policy, account adoption, and audit. Never remap domain ownership from provider emails.
8. Define at least three rehearsals: sanitized/local procedural, staging production-shaped, and final timed pre-cutover rehearsal. Set measurable time, consistency, RPO/RTO, error, and rollback acceptance thresholds.
9. Define rollback for every phase, including DNS not yet changed, Coolify warm state, reverse compatibility, destination discard/quarantine, queued work, new writes, and owner go/no-go authority.
10. Define a minute-by-minute cutover runbook draft, evidence template, operator roles, communications, incident path, and Commercial Stage 06 entry conditions.
