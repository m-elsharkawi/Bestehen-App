3. CI BUDGET — the hard operational constraint
================================================================================

GitHub Actions credits are nearly exhausted. Treat a CI run as a scarce, owner-authorized resource.

`.github/workflows/ci.yml` triggers on:
  - `pull_request` — ANY branch, and
  - `push` to `main` or to `implementation/personal-01..04-*`.

Therefore:
- Pushing `main` fires all seven jobs. You are working ON local `main` (section 2), so the danger
  here is a reflexive `git push`. Do not.
- A `pull_request` from ANY branch also fires the workflow. Never open one.
- Any branch NOT in that list can be pushed for free — useful only as an off-machine backup.
- Never run `gh` in a way that starts a workflow. If a stage rule appears to require a PR, stop and
  ask the owner rather than spending the run.

You must replicate CI locally instead. The seven CI jobs map to these commands:

    pnpm check          # policy, format, lint, typecheck, boundaries, unit, release, build, budget
    pnpm test:e2e       # browser + keyboard + reflow + axe, across chromium/firefox/webkit
    pnpm test:visual:container   # the pinned Chromium raster gate
    pnpm test:integration        # real PostgreSQL migration and recovery
    pnpm test:process            # worker startup, readiness, signal contract
    pnpm test:oci                # container identity

A stage is not verified until `pnpm check`, `pnpm test:e2e` and `pnpm test:visual:container` are
green on a committed tree, plus `test:integration` and `test:process` for any migration or worker
work this stage introduces.

4. LOCAL ENVIRONMENT — traps that have already cost real time
================================================================================

Toolchain
- The system Node is v22 and will NOT build this repo. Prefix every command:
  `export PATH=/Users/sharkawi/Developer/Bestehen/.toolchains/node-v24.19.0-darwin-arm64/bin:$PATH`
- Repo root is `/Users/sharkawi/Developer/Bestehen/App`.

Gate sequencing
- `pnpm check` runs `test:release`, which REFUSES a dirty worktree. Commit first, then verify,
  then amend if it fails. Do not tell a subagent to run `pnpm check` while it has uncommitted work;
  give subagents `pnpm lint && pnpm format:check && pnpm typecheck && pnpm test:unit` instead.
- `pnpm lint` (Biome lint) and `pnpm format:check` (Biome format) are SEPARATE. Passing lint does
  not mean formatting passes. Run both.
- `pnpm test:unit` repopulates `apps/web/.next` as a side effect, so a command chained after it can
  trip over build output that was not there when the chain started.

Running the app
- Fixture routes are double-gated and 404 without BOTH `BESTEHEN_APP_ENV=test` and
  `BESTEHEN_RELEASE_COMMIT=playwright-synthetic`.
- Start command:
  `BESTEHEN_APP_ENV=test BESTEHEN_RELEASE_COMMIT=playwright-synthetic BESTEHEN_AUTH_ADAPTER=fake BESTEHEN_AI_ADAPTER=fake BESTEHEN_EMAIL_ADAPTER=fake BESTEHEN_OBJECT_STORAGE_ADAPTER=fake BESTEHEN_STT_ADAPTER=fake BESTEHEN_TTS_ADAPTER=fake BESTEHEN_LOG_FORMAT=json BESTEHEN_LOG_LEVEL=info BESTEHEN_RELEASE_DIRTY=false BESTEHEN_SCHEMA_MIN_REVISION=<rev> BESTEHEN_SCHEMA_MAX_REVISION=<rev> DATABASE_URL=postgresql://synthetic:synthetic@127.0.0.1:5432/synthetic HOSTNAME=127.0.0.1 PORT=3300 node apps/web/.next/standalone/apps/web/server.js`
- STALE SERVER TRAP, which has produced confidently wrong measurements more than once:
  kill by port, not by process pattern — `kill -9 $(lsof -t -iTCP:3300)`. The process is named
  `next-server`, so `pkill -f "standalone/apps/web/server.js"` misses it. A surviving old server
  serves stale server-rendered HTML with freshly rebuilt CSS from disk, which looks plausible and
  is not. ALWAYS rebuild after changing source, and assert something in the served HTML that only
  exists after your change before you trust any measurement.
- `pnpm test:e2e` runs the standalone server directly and does NOT build first. Deleting `.next`
  before it will fail with "Process from config.webServer was not able to start".

Visual gate
- Regenerate baselines only in the pinned container: `pnpm test:visual:update`. Then prove it with
  `pnpm test:visual:container` (no `--update`). Regenerating and verifying are different claims.
- `maxDiffPixelRatio` is `0.0024`, not the 0.02 some older notes state.
- Small changes can legitimately fall inside tolerance and leave a baseline untouched; that is not
  staleness. Confirm with a non-update run.
- Never hand-edit files under `apps/web/tests/p04-visual.spec.ts-snapshots/`.

Browsers
- Run all three Playwright projects. A chromium-only run has already hidden a real cross-browser
  layout bug (`size` attribute acting as an intrinsic floor in firefox/webkit but not chromium).

Design board comparison
- Serve boards from the repo root (`python3 -m http.server 4400`), not `file://`, and inject the
  app's self-hosted WOFF2 before capturing, then assert `document.fonts.check(...)` is true.
  Without that the board silently falls back to system fonts and every type comparison is void.

Budget
- `pnpm check` enforces a 200 KiB gzip first-load budget. The protected route currently sits at
  ~196 KB — roughly 4 KB of headroom. Stage 05 adds substantial runtime surface, so treat the
  budget as a design constraint from the first subagent brief, not a late surprise.

5. DISK AND DOCKER HYGIENE — required, not optional
================================================================================

This machine has repeatedly hit 100% disk, which wedges the Docker daemon and produces misleading
errors. `apt` reporting "invalid signature / repository is not signed" inside a build is the
Docker VM's overlay being full, not a security or network problem.

Before any container work:
    df -h /System/Volumes/Data          # host
    docker system df                    # VM images / volumes / build cache
    docker run --rm <base> df -h /      # free space INSIDE the VM (the one that actually matters)

After every visual-gate or container run, and at the end of every subagent task:
    rm -rf apps/web/.next
    docker builder prune -af
    docker image prune -f               # dangling only

Rules:
- `docker image prune -f` (dangling) and `docker builder prune -af` (cache) are safe: regenerable.
- NEVER run `docker image prune -a`, `docker volume prune`, or delete `Docker.raw`. Tagged images
  and the 19 local volumes are the owner's data; some tagged images are locally built and exist in
  no registry. Deleting them is unrecoverable. If space is still short, list candidates and ask.
- The Docker VM is capped around 59 GB. Check headroom before starting a container build.
- `Dockerfile.visual` now caches its dependency layers above the source copy: a source edit
  rebuilds in ~17s instead of minutes. Do not "simplify" it by moving `COPY . .` back above the
  install — and note the `--offline` re-link after the copy is required, because
  `injectWorkspacePackages: true` means a manifest-only install injects empty package copies.

6. HOW TO SPLIT THE WORK
================================================================================

Planning (05P) must be accepted before any Execution (05E) subagent starts. Planning changes no
production code. That ordering is from the common contract and you may not relax it.

Beyond that, you choose the split. Judge it by these principles rather than a fixed recipe:

- Split along contract seams, not file counts. A subagent should own a coherent contract end to
  end (schema + implementation + tests) so it can verify itself.
- Prefer sequential execution wherever two tasks touch the same file. Stage 04 showed that three
  agents editing one stylesheet in parallel worktrees auto-merges silently and defeats review.
  Parallelize only across genuinely disjoint file sets, and say why you believe they are disjoint.
- Give every subagent: the common contract, its slice of the stage prompt, exact baseline SHA and
  branch, the previous handoff, the environment traps in section 4, the cleanup rules in section 5,
  and its precise Definition of Done with the commands that prove it.
- Any subagent touching the UI also gets the relevant sections of
  `Implementation/Personal/04-responsive-web-design-system/post-acceptance-corrections.md`. Without
  it they will reintroduce exactly what Stage 04's review pass removed: a card on `--surface-sunken`
  where the board lifts it, a heading at the browser-default 700, a filled control that is invisible
  against its dark surface, a new aside that silently takes the 2:1 split when it needs 7/5, or a
  duplicate theme control in the header.
- Forbid every subagent from: pushing `main`, opening a PR, running `gh`, editing visual snapshots,
  editing `Design/`, editing `Implementation/**/plan.md` outside its own stage artifact, and
  weakening a test to make a check pass.
- Decide per task whether the subagent commits on local `main` itself or leaves the tree dirty for
  you to review and commit. Leaving it dirty gives you a cleaner review, but only one subagent may
  run at a time under that arrangement. Either way, tell it explicitly which, and forbid pushing.
- Require measured numbers and the exact commands run — not adjectives.

Natural seams in Stage 05, offered as a starting point rather than a mandate: content manifest and
rights/provenance/versioning; publication, quarantine and withdrawal plus seed/import tooling; the
shared attempt state machine with timing, autosave, resume/expiry and idempotent submit/finalize;
deterministic scoring and the evidence proposal/acceptance path; Reading; Language Elements;
Listening media, playback and accessible alternatives; foundation/onboarding checkpoints. The
attempt runtime underpins all three skills — sequence it before them and treat a thin vertical
slice as its acceptance, exactly as 05P item 10 requires.

Model selection — match the model to the task, never max-by-default:
- Reserve the strongest model for genuine synthesis: the plan itself, the attempt state machine and
  its recovery semantics, evidence/validity contracts, and anything with no precedent to copy.
- Use a mid-tier model for well-specified implementation where the contract is already decided:
  variants against an accepted schema, test authoring, tooling, fixtures, mechanical refactors.
- State the model you chose for each subagent and why, in one line, in `handoff.md`.
- If a subagent dies partway (session limits happen), inspect the working tree before respawning.
  Finishing a small remainder yourself is often cheaper than a fresh expensive agent re-deriving
  context.

7. YOUR VERIFICATION DUTIES
================================================================================

A subagent's report is a claim, not evidence. For every completed task:

1. Read the actual diff. Do not accept a summary.
2. Re-run the gates yourself on a committed tree: `pnpm check`, `pnpm test:e2e`,
   `pnpm test:visual:container`, plus `test:integration` / `test:process` where relevant.
   Subagents routinely run a narrower set than they should.
3. Re-measure the claims that matter with your own script, against a server you rebuilt and
   confirmed is serving the new code.
4. Check what the subagent did NOT run. In Stage 04 the recurring gaps were: `format:check` skipped
   because `lint` passed; only chromium exercised; the full gate never run on a committed tree.
5. Look at rendered output for anything user-visible. Numbers passing is not the same as it looking
   right, and a screenshot captured from a stale server is worse than none.
6. Verify against the source of truth, not the intermediate. If a manifest claims a component maps
   to an anchor, open both.
7. When you change a verification script, prove the change does not narrow what it checks — diff
   the before/after result sets, not just the exit code.

Reject and re-task on: unverified claims, weakened tests, placeholder tests as evidence, secrets in
code/fixtures/logs, provider jargon in user copy, pass-probability language, silent history
rewrites, or accessibility regressions.
